1) Git clone 경로/이름 지정 & 삭제(주의)
clone할 때 폴더명 새로 지정 가능

삭제: rm 옵션 의미 (매우 위험)
rm -rf second-repo-copy/


rm : 파일/폴더 삭제

-r : recursive (폴더 내부까지 전부)

-f : force (확인 없이, 없는 파일 오류 무시)

안전한 삭제 습관

ls second-repo-copy/
rm -rI second-repo-copy/   # 중요한 경우 한 번 더 물어봄
rm -ri second-repo-copy/   # 하나씩 다 물어봄

6) merge vs rebase (충돌 해결 관점)
merge

“현재 브랜치에 다른 브랜치의 변경을 합친다”

git merge fizz


충돌 해결 후 merge 커밋 메시지가 미리 채워져 있음

rebase

“내 브랜치의 기반(base)을 최신 쪽으로 다시 맞춘다”

충돌 해결 후:

git rebase --continue


TIL 결론

대부분은 rebase보다 merge가 간단해서 실무에서도 merge가 더 흔함

git flow에서는 rebase를 제한적으로 쓰는 문화가 많음

7) Merge Conflict 표시 의미

충돌 파일을 열면 이런 마커가 나옴:

<<<<<<< : 내(현재) 변경 시작

======= : 경계선

>>>>>>> : 상대(병합 대상) 변경

해결 방법(현실적인 선택지)

둘 다 삭제(파국)

한쪽만 채택

둘 다 살리고 수동으로 합쳐서 새로운 정답 만들기 ✅(대부분 이게 정답)

충돌 났을 때 흐름

vi main.py   # 충돌 부분 수정
git add main.py
git commit   # merge면 merge 커밋
# rebase면:
git rebase --continue

8) FizzBuzz 구현 포인트 (버그에서 배운 점 포함)
요구사항

1~15

3의 배수: fizz
[O
5의 배수: buzz

15의 배수: fizzbuzz

그 외: 숫자

올바른 기본 구현
for i in range(1, 16):
    if i % 15 == 0:
        print("fizzbuzz")
    elif i % 3 == 0:
        print("fizz")
    elif i % 5 == 0:
        print("buzz")
    else:
        print(i)

(실수 포인트) 문법 오류

for i % 3 == 0 ... 같은 형태는 불가능

for는 반복 대상이 필요 → for i in range(...)

13) 원격 main 최신 가져와서 내 브랜치에 반영 (fetch + merge)
git fetch origin main
git merge FETCH_HEAD


의미:

fetch : 원격 main 최신 커밋을 “다운로드만”

merge FETCH_HEAD : 방금 가져온 그 커밋을 “현재 브랜치에 병합”

동일 표현:

git merge origin/main


언제 쓰나

PR 전에 내 브랜치가 오래돼서 충돌을 미리 해결하고 싶을 때

로컬에서 직접 merge 커밋 만들고 push할 때
